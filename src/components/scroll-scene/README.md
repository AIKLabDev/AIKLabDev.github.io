# 스크롤 3D 히어로 — A/B 실험

## 현재 실험: 섹션 스냅 (`hero_scroll_snap`)

| | `flow` (연속) | `snap` (섹션 스냅) |
| --- | --- | --- |
| 스크롤 | 브라우저 기본. 휠을 굴린 만큼 진행 | 휠·키·스와이프 **한 번에 한 섹션** |
| 이동 | 즉시 반영 | 1.1초 이징으로 다음 섹션 중앙까지 |
| 기본 스크롤 | 그대로 | `preventDefault` 로 가로챔 |

**비교하려는 것**: 끊어 넘기는 것이 서사를 잘 전달하는가, 아니면 스크롤을
빼앗겨 답답하다고 느끼게 하는가.

진행 표시·건너뛰기·섹션별 길이·섹션 CTA 는 **양쪽 공통**이다. (그 비교는
`hero_scroll_story` 로 이미 끝났고 B안이 채택됐다 — 커밋 8f2db04 참고)

## 지금은 실험이 꺼져 있다 (snap 전원 배포)

`ASSIGNED_VARIANTS = ['snap']` — 무작위 배정 풀에 snap 하나만 있어서
모든 방문자가 snap 을 본다. **전환 지표가 아직 없어 갈라봐야 데이터가 쌓이지
않기 때문이다.** 지표를 붙인 뒤 `['flow', 'snap']` 로 되돌리면 50/50 이 재개된다.

flow 는 비교용으로 여전히 열린다:

```
/?hero=snap    섹션 스냅 (현재 전원 기본값)
/?hero=flow    연속 스크롤 (배정 풀 밖. 강제 지정으로만 열린다)
```

렌더된 변형은 히어로 섹션의 `data-hero-variant` 속성으로 확인할 수 있다.

⚠️ `DEFAULT_VARIANT` 는 기본값처럼 보이지만 **브라우저에서는 쓰이지 않는다**
(`typeof window === 'undefined'` 분기 전용 = 사실상 SSR 전용). 실제로 무엇이
보일지는 `ASSIGNED_VARIANTS` 가 정한다.

저장된 배정이 현재 풀에 없으면 새로 배정한다. 이 검사가 없으면 `?hero=flow` 를
한 번 열어본 사람은 전원 배포 이후에도 계속 flow 를 보게 된다.

## 스냅 구현에서 실제로 어려운 지점

`useSectionSnap` 이 처리하는 것들. 순서대로 전부 실제 함정이다.

1. **passive 리스너** — `window`·`document`·`body` 의 wheel 리스너는 Chrome 기본이
   passive 라 `preventDefault()` 가 조용히 무시된다. `{ passive: false }` 필수.
2. **트랙패드 관성** — 한 번 튕기면 delta 가 감쇠하며 수십~수백 개가 들어온다.
   "애니메이션 끝나면 해제" 만 하면 해제 직후 잔여 관성이 다음 섹션을 즉시
   트리거해 한 번에 두세 섹션이 넘어간다. → 입력이 조용해질 때까지
   (`snap.quietMs`) 더 잠가둔다. 잠긴 동안 들어오는 입력마다 타이머를 다시 건다.
3. **wheel 만 막으면 안 된다** — 키보드·터치가 네이티브로 돌면 같은 페이지에
   스크롤 모델이 두 개 생긴다. `keydown`(↑↓/PgUp/PgDn/Space)·`touchmove` 도 같이 잡는다.
   `Home`/`End`/`Tab` 은 일부러 두었다 — 탈출 경로까지 막으면 안 된다.
4. **양 끝은 가로채지 않는다** — 첫 섹션에서 위, 마지막 섹션에서 아래는 네이티브에
   넘겨야 히어로 밖으로 정상적으로 나갈 수 있다.
5. **`scroll-behavior: smooth`** — `index.css` 에 걸려 있어서 `scrollTo` 에
   `behavior: 'instant'` 를 명시하지 않으면 브라우저가 자체 애니메이션을 돌려
   우리 rAF 루프와 싸운다.
6. **이중 이징** — 스크롤이 이징으로 움직이는데 카메라 감쇠까지 느리면 끈적하게
   느껴지고, 반대로 감쇠가 너무 빠르면 카메라가 스크롤에 못박힌 듯 딱딱해진다.
   둘은 같이 맞춰야 하는 값이다 (현재 1.1초 / 감쇠 8 — 아래 튜닝 항목 참고).

`prefers-reduced-motion` 사용자는 애초에 3D 히어로를 받지 않으므로 이 훅도
마운트되지 않는다. 스크롤 재킹은 전정기관 증상의 대표적 유발 요인이라
이 폴백이 특히 중요하다.

## 감각 값 튜닝

스크롤 속도·감쇠는 숫자로 정해지지 않고 만져봐야 정해진다. 리빌드를 돌지 않도록
개발 중에는 URL 로 바로 바꿀 수 있다.

```
/?hero=snap&snapDuration=1400        한 섹션 이동 시간(ms). 카메라 이동 속도와 같다
/?hero=snap&camDamp=6                카메라 추종 강도. 낮을수록 여운이 남는다
/?hero=snap&snapQuiet=200            관성 차단 대기(ms). 한 번 튕겼는데 여러 섹션이
                                     넘어가면 올린다
```

마음에 드는 값을 `sceneConfig` 에 적으면 된다 (`cameraDamping`, `snap.*`).

`sceneConfig` 에는 조명(`lighting`)과 피사체 프레이밍(`framing`)도 들어 있다.
조명을 다시 맞출 때 컴포넌트가 아니라 `data/scrollScene.js` 한 곳만 열면 된다 —
`SceneStage` 는 배선만 한다. `tune()` 은 프로덕션 빌드에서 인자를 그대로 돌려주는
함수로 접혀 아무 일도 하지 않는다.

현재 기본값: `duration` 1100ms · `cameraDamping` 8 · `quietMs` 120 · `touchThreshold` 40px

## 카메라는 통로 한쪽에만 서지 않는다

화면에서 차량이 어느 쪽으로 달리는지는 시선의 z 부호가 정한다 (화면 오른쪽 =
`cross(시선, 위)`). 여섯 장을 다 한쪽에 두면 처음부터 끝까지 한 방향으로만 흐른다.

| | 자리 | 화면에서 달리는 쪽 |
| --- | --- | --- |
| ① | 앞·+z (6.6m) | 오른쪽 |
| ②③ | **바로 뒤** (z=0) | 없다 — 화면 안쪽으로 멀어진다 |
| ④ | 뒤·+z | 오른쪽 |
| ⑤⑥ | 뒤·-z (통로 건너) | 왼쪽 |

②③ 이 대각이 아니라 정후방인 것이 이 두 장의 연출이기도 하다. 점 구름 열이 좌우
대칭으로 서서 통로가 통째로 보이고, 경로가 휘는 것이 그대로 좌우로 읽힌다. 둘은
같은 자리에서 거리만 다르다 — ② 는 인식하는 **범위**를 보여 주므로 멀찍이(28m),
③ 은 경로가 **어떻게** 휘는지를 보여 주므로 바짝(17m) 붙는다.

## ③ 의 경로는 앞으로만 뻗지 않는다

한 줄만 그리면 화면 아래에서 위로 곧게 뻗은 선 하나로 읽힌다 — 갈 수 있는 곳이
앞뿐인 것처럼 보인다. `route.branches` 가 **옆 통로로 갈라지는 길**을 같이 깐다.
4분원으로 꺾어 든 뒤 곧게 뻗으므로 이어 붙는 자리에서 기울기가 같고, 밝기가 서로
어긋나게 오르내려 계속 다시 재고 있는 것으로 읽힌다.

**갈림목은 세계에 못 박혀 있다.** 차량에서 뻗어 나가는 것이 아니라 앞에서 흘러와
지나간다 — 옆 통로는 창고에 있는 것이지 차량에 붙어 있는 것이 아니다.

**갈래가 랙을 뚫고 나가면 안 된다.** 블록은 매 주기의 마지막 `block.gap` 미터까지
오지 않으므로(`x0` 지터가 거기까지만 허용된다) 그 구간이 어느 열에서도 비어 있는
옆 통로다. 갈림목 자리(`base`)와 꺾어 도는 반지름(`radius`)의 합이 그 안에 들어와야
한다 — 지금은 13.5m 에서 꺾어 16.7m 에서 열을 빠져나간다 (빈 구간 13.5~18m).

## 차량이 통로를 바꿔 타게 만들어 봤다 (되돌림)

②③ 에서 곧게만 달리는 것이 심심해 `course` 를 넣어 봤다 — 꺾어 들어가 옆 통로를
달리다 다시 꺾어 나오는 주행이고, 프레임을 지키려고 카메라도 같이 옮겨 갔다. **주행이
이상해 보여 전부 뺐다.** 다시 만들 사람을 위해 부딪혔던 것만 남긴다.

- **경로가 `y = f(주행거리)` 라 90도로 꺾을 수 없다.** 기울기가 무한대가 되는 자리를
  만들 수 없어 50도가 한계고, 그 정도로는 "돌았다"가 아니라 "미끄러졌다"로 보인다.
  진짜 직각으로 꺾으려면 세계를 차량 기준으로 **회전**시켜야 하는데, 점 구름·랙 열·
  바닥 격자가 전부 주행축 한 방향으로만 접히는 지금 구조가 그 자리에서 무너진다.
- **켜고 끄는 것은 도는 중이 아닐 때만 해야 한다.** 도는 중에 가중치로 끄면 차량이
  조향 없이 옆으로 밀린다. 한 번의 주행 밖에서 값도 기울기도 0 이 되는 곡선으로
  두고 거기서만 바꿔야 한다.
- **적재 지점 앞뒤 `laneRun` 은 곧게 펴야 한다.** 포크가 팔레트에 들어가려면 차선
  한가운데라야 한다. 시간이 아니라 자리로 닫아야 지점에서 값도 기울기도 0 이 된다.
- **회피와 섞이지 않게 해야 한다.** 화물은 통로 한가운데에 있으므로, 주행이 옆 통로로
  간 구간에서는 피할 것도 인식 표시를 켤 것도 없다.

-z 는 키라이트(`lighting.key`) 반대쪽이라 옆면이 어둡다. 멀리서 보는 ⑤⑥ 은 괜찮지만
바짝 붙는 장을 이쪽에 두면 검은 덩어리가 된다.

## 앞의 세 장은 점 구름, 뒤의 세 장은 실물이다

①~③ 은 센서가 그려 나가는 공간이라 점으로만 서 있고 (`stages/pointField.js`),
④~⑥ 은 실제로 일하는 현장이라 실물 지오메트리로 선다 (`stages/yard.js`).
**③→④ 에서 둘이 자리를 바꾸는 것이 그대로 연출이다** — 점으로 알던 공간이 랙과
트럭과 화물로 바뀐다. 두 세계가 겹치지 않도록 가중치는 서로의 여집합이다.

```
점 구름 = mapping + routing        실물 = docking + fleet + join
```

### 점 구름 (①~③)

창고는 **점으로만** 서 있다. 랙 열·외벽·기둥이 지오메트리 한 덩이(`THREE.Points`)이고,
접기와 드러남을 전부 정점 셰이더에서 계산한다. 매 프레임 수만 개의 행렬을 다시 쓰지
않아도 되므로 **화면을 가득 채울 만큼** 점을 깔 수 있고, 화면이 점으로 가득 찬다는
사실 자체가 "넓은 공간"이라는 인상을 만든다.

예전에는 창고를 세우지 않았다. 어두운 바닥과 좌우 6m 짜리 점 울타리뿐이었는데, 그러면
카메라를 아무리 빼도 볼 것이 없어 **좁은 관 속을 달리는 것으로 읽힌다.** 실물 랙을
세우면 주인공과 문구가 배경과 자리를 다투지만, 점은 다투지 않는다.

내용은 `data/heroStages.js` 에 있고, 장마다 무엇을 보여줄지는
`scrollSections[].beat` 가 가리킨다.

| 장 | 연출 | 차량이 하는 일 | 같이 보이는 것 |
| --- | --- | --- | --- |
| 01 오프닝 | `opening` | 달린다 | **없다** (차량 한 대만 서 있고, 카메라가 빠지며 공간이 드러난다) |
| 02 인식·측위 | `mapping` | 달린다 | LiDAR 스윕, 센서 앞에서 돋아나는 점 구름 |
| 03 자율주행 | `routing` | 달리면서 **서지 않고** 비켜 간다 | 이미 다 그려진 공간, 바닥 경로, 장애물과 인식 표시 |
| 04 화물취급 | `docking` | 적재 지점마다 팔레트를 집어 트럭에 싣고, 그 트럭을 지나쳐 다음 지점으로 나아간다 | 대기 화물 격자, 도크에 늘어선 트럭, 랙을 채우는 동료 차량 |
| 05 현장 | `fleet` | 통로를 떠나, 화물로 세운 글자 위에서 한 장을 옮긴다 | 광장 — `AIKOREA` 와 오가는 AMR 네 대 (세계는 멈춘다) |
| 06 합류 | `join` | 광장에서 하던 일을 계속한다 | 광장 (카메라만 조금 더 오른다) |

**세계는 ① 에서만 비어 있고 ②~④ 내내 서 있는다.** 옅어지는 순간 "같은 공간을 계속
달린다"가 무너진다 — 예전에는 ③ 에서 벽이 35% 로 꺼졌고, 하필 공간이 열려야 할 그
순간에 화면이 비었다.

⑤ 는 이 규칙을 **의도적으로** 깬다. 무너지지 않는 이유는 적재장이 그 자리에서 꺼지는
것이 아니라 뒤로 흘러 지나가고(`dock.linger`), 그 위로 광장이 겹쳐 들어오기 때문이다.
정말 지켜야 하는 것은 "무대가 사라지지 않는다"가 아니라 **"덮이는 총량이 뜻하지 않게
줄지 않는다"** 다 — `HeroScene` 이 이웃한 두 장의 가중치를 **더하므로**(`add()`),
서로 마주 보는 페이드 둘이면 합이 1 로 유지된다.

### ②→③ 은 드러나는 방식이 바뀌는 것이다

같은 점 구름을 두 곡선 중 하나로 드러낸다 (둘 다 차량 기준 X, `[드러나는 지점, 그 폭,
사라지는 지점, 그 폭]`).

| | `building` — ② | `built` — ③ 부터 |
| --- | --- | --- |
| 값 | `[10, 4.5, -22, 8]` | `[58, 18, -58, 20]` |
| 보이는 것 | 센서 앞 10m 에서 점이 돋아난다 | 116m 짜리 공간이 통째로 서 있다 |

`uCurve` 가 이 둘을 섞는다. **이 전환 자체가 ②→③ 에서 공간이 열리는 연출이다** —
카메라도 같이 물러나므로 "센서가 그려 나가던 것" 이 "이미 아는 공간" 으로 바뀐다.

### 점은 적은 수의 덩어리에 몰아줘야 읽힌다

두 번 실패한 자리다.

- **모서리만 찍으면** 비스듬히 볼 때 사선 점열이 되어 형태가 사라진다.
- **성기게 넓게 뿌리면** 점만 많고 면이 만들어지지 않는다.

그래서 랙 열은 겉면을 **촘촘히** 표본한 상자이고 (`putBlock`), 열 수는 셋뿐이다.
통로에 면한 쪽 면만 찍는다 — 반대쪽 면은 상자 뒤라 형태에 보태는 것 없이 점만 두 배가
된다. 먼 열일수록 표본 간격을 넓힌다 (`rack.falloff`).

**모든 점은 구조물 위에 있어야 한다.** 천장 트러스·바닥 통로선·부유 입자를 얹어 봤는데,
아무리 규칙적으로 깔아도 화면에서는 붙을 데 없이 떠도는 특이점으로만 읽혀 전부 뺐다.
지금 남은 것은 랙 블록·외벽·기둥뿐이다.

**상자가 전부 같으면 벽지 무늬가 된다.** 그래서 칸마다 길이·깊이·높이가 다르고, 일부
칸은 비워 둔다 (`block.length`, `rack.depth`, `rack.height`, `rack.empty`). 높이만은
**열 기본값을 뽑고 칸마다 그 값에서 흔든다** (`rack.spread`) — 칸마다 독립으로 뽑으면
한 줄 안에서 들쭉날쭉해 랙이 아니라 잡동사니로 보인다.

**그러면서도 ④ 의 실물 랙 열과 닮아야 한다.** ③→④ 는 같은 창고가 점에서 실물로
바뀌는 장면이라, 치수가 크게 다르면 창고가 통째로 갈린 것으로 보인다. 실물은 깊이
1.1m · 높이 6.1m 짜리 **얇고 높은 벽**이 통로에서 10m·21m 에 서 있다 — 예전에는 여기
직육면체가 깊이 4~7.5m · 높이 2.4~6.2m 짜리 두꺼운 덩이라 넘어가는 자리에서 형상이
튀었다. 얇게 만든 만큼 표본 간격(`rack.step`)을 좁혀야 점 수가 유지된다.

**스크롤이 정하는 것은 어느 연출을 얼마나 보여줄지와 카메라 구도뿐이다.** 장비는
시간축으로 계속 움직인다 — 스크럽(스크롤 = 애니메이션 시각)으로 묶으면 사용자가
멈추는 순간 장비도 얼어붙어 정지 화면이 된다.

### 여섯 장이 무대 하나를 같이 쓴다

여섯 장은 **한 대가 한 번 달리는 동안** 벌어지는 일이다. 장마다 무대를 주면 장이
바뀔 때 서로 다른 세계의 차량이 동시에 디졸브되어 **화면에 두 대가 겹친다.** 그래서
무대 인스턴스는 하나뿐이고, 디졸브되는 것은 연출(점·경로·라벨)뿐이다.

그래서 `HeroScene` 은 같은 무대·같은 연출을 가리키는 두 장의 가중치를 **더한다.**
큰 쪽만 쓰면 전환 한가운데에서 0.5 가 되어, 계속 보여야 할 차량이 반투명해진다.

### 전부 트레드밀이다

차량은 원점에 서서 바퀴만 돌고 세계가 뒤로 흘러간다. 순환 루프로 만들면 아무리 크게
잡아도 같은 자리가 돌아와 반복이 드러나는데, 흘려보내는 방식은 끝이 없다.

트레드밀이라야 **"계속 주행한다"와 "장을 자유롭게 오간다"가 같이 성립한다.** 차량이
실제로 전진하면 되돌아갈 때 원점으로 데려오는 구간이 필요하고, 그 구간은 화면에
보여줄 수 없다.

점·장애물·라벨도 같은 방식으로 흐른다. 주기적으로 깔아 두고 창 전체로 접으면, 접히는
순간 모든 요소가 정확히 이웃 요소의 자리로 가므로 그림이 변하지 않는다. 드러나는
정도를 **위치만의 함수**로 두는 것이 조건이다 — 지나온 시간을 기억하게 만들면 접히는
자리에서 상태가 튄다.

### ④ 도 계속 앞으로 나아간다 — 그래야 지울 것이 없다

한 번은 왕복으로 만들어 봤다. 같은 자리로 돌아오니 실은 팔레트를 지우고 새 팔레트를
만들어 놓아야 했고, **화면에서 물건이 사라졌다 나타나는 것이 그대로 보였다.**

앞으로 나아가면 그럴 일이 없다. 한 바퀴마다 `stride` 만큼 전진하므로 모든 것이
흘러 지나갈 뿐이다.

| | 어디서 오는가 | 어디로 가는가 |
| --- | --- | --- |
| 대기 화물 | `stride` 격자 위에 깔려 안개에서 흘러온다 | 집힌 자리는 화면 뒤로 빠진 뒤 되채워진다 |
| 실은 팔레트 | 포크 위 팔레트가 그대로 적재함 팔레트가 된다 | **트럭에 남는다** |
| 트럭 | 같은 격자 위에 한 대씩 서서 안개에서 흘러온다 | 한 장을 받고 그 자리에 남는다 — 차량이 지나쳐 간다 |
| 랙 채우는 차량 | 지나가는 동안 한 번 작업한다 (위치의 함수) | 접히는 자리는 화면 밖이다 |

**바꿔 다는 순간은 전부 같은 자리에서 일어난다.** 격자의 팔레트 → 포크 위 팔레트,
포크 위 팔레트 → 적재함 팔레트. 자리도 모양도 같으므로 즉시 바꿔 달아도 보이지 않는다.

| 단계 | 하는 일 |
| --- | --- |
| `approach` | 등감속으로 적재 지점에 **정확히** 선다 (`v = sqrt(2ar)`) |
| `pick` → `lift` → `hold` | 포크가 팔레트 밑으로 들어가고 들어 올린다 |
| `haul` | 트럭 차선으로 옮겨 가며 마스트를 적재함 높이까지 올린다 |
| `place` | 포크를 내려 팔레트를 적재함에 넘긴다 |
| `back` | 통로 쪽으로 휘며 물러난 뒤 다음 지점으로 향한다 |

### 트럭은 세워 두고 차량이 지나간다

한 번은 트럭을 오게 만들어 봤다. 한 장을 실은 트럭이 통로로 빠지고 다음 트럭이
뒤에서 들어오는 연출인데, **여기서 고쳐야 할 것이 셋이었다.** 실은 트럭은 문을 연
채 떠나고, 들어오는 트럭도 문을 연 채 오고, 들어오면서 그리는 사선이 바닥 화물을
가로지른다. 문·속도·차선을 다 맞춰도 트럭 두 대가 좁은 통로에서 서로를 스친다.

세워 두면 셋 다 없다. 트럭은 대기 화물과 **같은 `stride` 격자** 위에 한 대씩
후면을 열고 서 있고, 차량이 한 대를 채우고 지나쳐 다음 대로 간다. 도크에 트럭이
늘어선 그림이 현장에 더 가깝기도 하다.

대신 **차량이 트럭을 지나갈 수 있어야 한다.** 세 가지가 붙는다.

- 후진은 포크가 빠질 만큼(`tineOut`)이 아니라 적재함 뒷면 **뒤까지**(`backRun`)
  물러난다.
- **후진은 들어온 곡선을 되짚지 않는다** (`backLane`). 되짚으면 물러난 자리에서
  차체가 아직 트럭 쪽으로 28도 틀어져 있고, 앞으로 돌아서는 순간 그 요각이
  **한 프레임에 0 으로 펴진다.** 양 끝에서 기울기가 0 인 곡선을 따로 두면 운반
  구간과도 이어지는 주행과도 같은 기울기로 만난다.
- 지나가는 동안은 통로 반대쪽으로 부풀린다 (`pass`). 카메라가 트럭 너머에 있어서
  통로 한가운데로 지나가면 트럭이 주인공을 가린다. 종은 양 끝에서 값도 기울기도
  0 이라, 물러난 자리와 다음 적재 지점 사이에 들어가기만 하면 이어 붙는다.

**단계는 차선보다 먼저 넘어간다.** 차선을 정할 때 `s.step` 을 읽으면 물러나기를
끝낸 그 한 프레임이 이미 `approach` 라 운반 곡선으로 돌아가고, 거기서 요각이
0.46rad 튄다. 이 프레임이 무엇이었는지를 지역 변수로 남겨 두고 그것으로 고른다.

**부풀린 폭은 옆 통로와 겹치면 안 된다.** 랙을 채우는 차량이 물러나 서는 자리
(`loader.rack - 4.6`)가 부풀린 끝(+1.7)에 닿으면 둘이 서로를 통과한다.

### 차선은 시간이 아니라 거리로 옮긴다

지수 추종으로 옮기면 초반에 몰려 앞으로 가는 것보다 옆으로 가는 속도가 커지고,
차량이 진행 방향과 무관하게 게걸음을 친다. 거리의 함수로 두면 기울기가 그대로
진행 방향이 되고 최대치도 `폭 × f'max / 거리` 로 묶인다.

**두 가지가 더 필요하다.**

- 운반 구간은 **다음** 적재 지점이 아니라 **떠나온** 지점에서 잰다. 다음 지점을 잡는
  순간 진행률이 0 으로 돌아가 차선이 튀고, 차량이 홱 돌아간다.
- 곡선은 `smoothstep` 이 아니라 2차 도함수까지 양 끝에서 0 인 것을 쓴다
  (`6t⁵-15t⁴+10t³`). smoothstep 은 끝에서 2차 도함수가 6 이라 차선을 다 옮기고 선 뒤에도
  핸들이 꺾인 채 남는다.

속도로 나누는 식은 어디에도 두지 않는다 — 멈추는 순간 0 으로 나누게 되고, 그것을
막으려 하한을 걸면 하한에 닿는 자리에서 요각이 튄다.

**마스트가 닿는 높이가 연출을 정한다.** URDF 의 `fork_lift_joint` 상한이 0.88m 라
팔레트를 들 수 있는 최대 높이는 1.02m 다. 트럭 적재함 바닥(0.885m)은 이 한계 안에
들어오지만 랙은 맨 아래 칸(0.60m)만 닿는다 — 그래서 트럭은 주인공이 싣고, 랙은
옆 통로의 동료 차량이 맨 아래 칸에 넣는다. 한계를 넘겨 그리면 포크가 마스트에서
빠져나온다.

### 랙은 소스가 아니라 크기가 틀렸다

`rack_unit.obj` 는 **손으로 쌓는 선반**이다. 칸이 0.65m 폭 × 0.66m 높이 ×
0.80m 깊이라, 팔레트(1.02 × 1.22 × 1.19)를 넣으면 위 선반 둘을 뚫고 올라가고
옆 기둥에도 걸린다. 처음엔 얹는 화물을 한 켜로 낮춰 봤는데, 그러면 랙에 싣는
것이 통로를 달리는 것과 다른 물건이 된다.

늘리는 쪽이 맞다. 시뮬레이터가 쓰는 하이베이 랙(`demo-main` 의
`threejs_demo/app.js`, `WAREHOUSE_RACK_SIZE` 와 `shelfZ = [1.93, 3.68, 5.43]`)이
**칸 높이 1.75m** 다. 여기에 맞춰 메시를 `yard.rack.size` 로 늘리면
칸이 1.63 × 1.75 × 1.10m 가 되고 팔레트가 그대로 들어간다.

**선반 높이도 칸 폭도 늘린 값에서 나온다** (`rackMetrics`). 설정에 남는 것은
원본 메시 실측값(`decks`)과 목표 크기(`size`)뿐이라, 메시를 다시 구우면
`rackProp` 만 바뀌고 나머지는 따라온다.

기둥이 랙 한가운데(x≈0)에 서 있어서 **넣는 칸은 반 칸 밀어** 잡고, 팔레트는
깊이 한가운데가 아니라 **앞 빔에 맞춰** 놓는다 — 안쪽으로 들이밀면 마스트가
랙 안으로 들어간다.

**칸에 넣는 것은 칸 안에 들어가야 한다.** 상자 두 켜 × 두 줄(1.02 × 0.82m)이
칸(1.63 × 1.10m)에 들어가는 한계다. 세 줄(1.22m)이면 선반 밖으로 나와 기둥과
겹치고, 겹친 자리가 흐르면서 **지직거린다.**

**상자 메시는 원점이 바닥면이다** (`box.obj` 의 z 가 0→0.35). 가운데인 줄 알고
반 켜를 더하면 선반 위 화물이 통째로 0.17m 떠 있다 — 랙이 작을 때는 안 보였고
늘리고 나서 드러났다.

**선반은 앞뒤 빔 둘뿐이다.** 사이가 0.86m 비어 있어 화물을 그냥 얹으면 바닥에
닿은 것이 아니라 허공에 걸쳐 뜬 것으로 보인다 — 파렛트 랙이니 당연히 **팔레트가
빔을 건너질러야** 한다. 실물 메시는 4,390 삼각형이라 수백 장을 깔 수 없어, 랙에
깔리는 것만 상판 한 장과 받침 셋(48 삼각형)으로 줄이고 색은 실물 텍스처의
평균값을 쓴다. 통로에 놓이는 것과 포크에 실리는 것은 그대로 실물이다.

**랙을 채우는 차량은 위치의 함수라 주인공이 후진하면 되감긴다.** 세계가 앞으로
흐르니 이 차량의 위치도 되돌아가고, 하던 작업을 거꾸로 재생한다. 한 바퀴 안에서는
진행도가 내려가지 않게 묶고, 감기는 자리에서만 푼다.

**한 대만 움직이면 현장이 아니라 전시가 된다.** 주인공이 트럭을 싣는 동안 동료 차량이
랙을 채우고, 옆 통로로 다른 차량이 지나간다 (`yard.fleet`).

### 실물은 인스턴스 한 덩이에 담고 열째로 민다

랙 열은 `InstancedMesh` 하나다. 열이 `spacing` 주기로 반복되므로 열 전체를
`-(travelled mod span)` 만큼 밀면 접히는 자리에서 그림이 변하지 않는다. 이때
인스턴스는 `[-span, 2·span)` 을 덮어야 한다 — `[0, span)` 만 깔면 미는 순간 앞이나
뒤가 빈다.

**미는 것으로 잇는 것은 전부 진짜로 주기적이어야 한다.** 이건 열 자체보다
**열에 실린 것**에서 먼저 깨진다.

- 칸을 채울지 말지를 `[-span, 2·span)` 전체에 대해 뽑으면, 열은 그대로인데 실린
  것만 주기마다 달라 접히는 자리에서 **창고가 통째로 갈리는 것처럼 보인다.**
  한 주기(`units` 칸)만 뽑아 세 번 되풀이해야 한다.
- 바닥 화물은 한 주기만 깔고 무리째 밀고 있었다. `span` 을 다 밀면 무리가 통째로
  뒤로 빠져 **앞이 텅 비고, 감기는 순간 한꺼번에 되돌아온다.** 이쪽도 세 벌이다.

두 벌로는 모자란다 — 감기기 직전과 직후에 화면에 남아 있는 벌이 달라져 뒤쪽이
비어 보인다. 앞쪽 `[span, 2·span)` 너머는 안개 너머라 비어도 드러나지 않는다.

**열은 안개에 묻힐 만큼 길어야 한다.** 짧으면 통로가 끝나는 자리가 보여 관 속으로
읽힌다. 지금은 `span` 108m 에 세 벌이라 ±108m 까지 이어진다.

`obj2gltf` 는 MTL 의 `Ks` 를 metallic 으로 옮긴다. 트럭과 랙이 금속 1.0 / 거칠기 1.0
으로 나와 어떤 조명에서도 검은 덩어리가 되므로 `buildLibrary` 에서 다시 잡는다.

### 도킹만 시간이 아니라 거리로 닫힌다

나머지는 전부 초 단위로 도는데 접근 구간만 거리로 돈다. `v = sqrt(2ar)` 은 등감속이라
유한한 시간에 **정확히** 남은 거리를 0으로 만든다. 속도를 남은 거리에 비례시키면
(`v ∝ r`) 지수적으로 다가가기만 하고 영영 닿지 않아 포크가 팔레트에 들어가지 못한다.

팔레트는 실리기 전에는 세계에 놓여 다가오고 실린 뒤에는 포크를 따라간다. 멈춰 선
순간 두 식이 같은 자리를 가리키므로 부모를 바꿔 달지 않아도 이어 붙는 곳이 없다.

이음매를 없애는 것은 나머지 연산 하나다. 주기적인 것을 `-(달린 거리 mod 주기)` 만큼
밀면 한 칸을 지나갈 때마다 배열이 정확히 자기 자신으로 되돌아온다 — **격자만 세계에
못 박혀 있으면 차가 서 있는 것이 그대로 들통난다.**

공용 바닥 격자의 주기는 `lcm(cellSize, sectionSize)` 다. drei `Grid` 의 `sectionSize` 는
칸 수가 아니라 굵은 선 사이의 **거리**라, 얇은 선만 맞는 값으로 접으면 굵은 선이 접힐
때마다 옆으로 튄다.

점 구름은 `world.span`(180m) 으로 접는다. **접히는 자리가 보이지 않으려면 span 이
드러나는 창(`built` 기준 약 116m)보다 넓기만 하면 되고, 그 안의 배치는 주기적일 필요가
없다.** 다만 주행 방향으로 반복되는 것(블록 주기·기둥 간격·트러스 간격·출입구 주기)은
전부 span 의 약수여야 한다 — 나누어떨어지지 않으면 접히는 자리에 반 칸짜리 기둥이나
잘린 출입구가 드러난다. 같은 이유로 **랙은 자기 칸을 넘어가면 안 된다.** 칸을 통째로
반 칸씩 밀어 두 줄을 어긋내 봤는데, 마지막 칸이 span 을 넘어 접히는 자리에서 랙이 두
동강 났다. 어긋내는 것은 칸 **안에서** 민다.

격자는 어둡게 눌러 둔다. 밝으면 점 구름을 덮어 버려 창고가 다시 평면 도면으로 읽힌다.

### ⑤ 는 축척이 바뀌는 자리다 — 적재장을 지나쳐 광장으로

⑤ 를 네 번 잘못 만들었다. 바닥에 연구 영역 이름 넷을 띄웠고(눈이 이름이 아니라 옆의
화물로 흩어졌다), 통로 한쪽에 컨베이어와 팔레타이징 로봇을 세웠고(불투명도로
나타나는 세트는 "지나간다"가 아니라 "바뀐다"로 읽힌다), 좌표를 버블로 띄웠고,
글자를 통째로 흘려보냈다(스크롤 어디에서 멈추든 낱말이 잘렸다).

남은 답은 **카메라를 통로에서 떼어내는 것**이었다. ⑤ 에서 세계가 멈추고
(`targetSpeed = C.speed * (1 - above)`), 랙 열·바닥 화물·적재장이 걷히고, 카메라가
44m 위로 올라가 앙각 70도로 내려다본다. ①~④ 가 한 대를 따라왔으므로 여기서
주인공이 작아지는 것 자체가 "한 대가 전부가 아니다"가 된다.

세트 교체처럼 보이지 않는 것은 **④ 가 꺼지는 게 아니라 끝나기 때문이다** (아래 절).
그 위에 서는 광장(`stages/plaza.js`)은 세계 좌표에 못 박혀 있어 스크롤 어디에서
멈추든 같은 그림이다.

**카메라와 표적의 x 가 같아야 한다.** 화면 오른쪽은 `cross(시선, 위) = (-dz, 0, dx)`
라, x 로 비켜서면 그만큼 바닥이 기울어 글자가 대각선으로 눕는다. 통로 -y 쪽
(world +z)에 서는 것도 조건이다 — 반대편이면 글자가 거꾸로 읽힌다.

### 글자는 서 있고, 화물이 옮겨 다닌다

광장은 `AIKOREA` 를 5×6 격자에 화물 88 무더기로 쌓아 세운다. 그 위에서 AMR 네
대가 하는 일은 하나뿐이다 — **한 글자에서 한 장을 집어, 다른 글자의 빈 자리에
놓는다.** 세 번째 일마다 한 대는 든 채로 화면 밖까지 나가고, 반대쪽 밖에서 다른
한 대가 들고 들어와 채운다.

여기서 배운 것들:

- **저절로 사라지는 화물이 하나라도 있으면 전부 거짓말이 된다.** 앞선 판은 가까이
  온 차량 주변의 칸을 종 모양 곡선으로 흩었다가 되붙였는데, 인과가 없으니 그냥
  깜빡이는 것으로 읽혔다. 지금은 칸이 비는 유일한 이유가 "누가 집어 갔다"이고,
  채워지는 유일한 이유가 "누가 가져다 놓았다"다.
- **칸도 포크에 실린 팔레트와 같은 각도라야 한다.** 실린 팔레트는 차량과 같이 도는데
  차량은 언제나 화물을 마주 보고 드나든다 — 칸을 yaw 0 으로 깔면 집는 순간에 화물이
  90도 돌아앉는다. 칸 기준 자세는 `FACING`(π/2) 다.
- **바꿔 다는 순간은 갈래가 바닥 높이(`entry`)를 지날 때다.** 집을 때는 들기 직전,
  놓을 때는 다 내린 뒤. 가운데에서 바꾸면 화물이 공중에서 튄다.
- **차량이 들어가는 열은 드나드는 쪽이 다 비어 있는 열뿐이다.** 안쪽 칸을 고르면
  앞줄 화물을 뚫고 지나간다. 그래서 집는 자리는 "앞이 다 빈 열의 맨 앞 화물",
  놓는 자리는 "그 앞 빈 칸 중 가장 안쪽"이다.
- **적치대는 두 장을 넘기지 못한다**(`buffer.cap`). 상한이 없으면 놓을 자리를
  못 찾은 차량이 계속 쌓아 올려 세 장이 세로로 선다 — 그러면 그것이 낱자 옆에
  선 획으로 읽혀 **`AIKOREA` 에 없는 글자가 하나 생긴다.** 여기가 차는 것은
  `damage` 에 세지 않으므로 글자 쪽 상한이 이것을 막아 주지 않는다. 넘치는
  화물은 화면 밖에서 기다린다.
- **한 통로만 쓰면 한 줄만 갉아먹힌다.** 아래 통로에서만 드나들게 했더니 글자
  아랫줄이 통째로 사라져 `E` 가 `F` 로, `R` 이 `P` 로 읽혔다. 위 통로로 드나드는
  차량을 따로 두어 손상을 두 줄로 나눈다.
- **동선은 U자 3차 베지에 하나면 된다.** 도크에서 곧게 물러나 제자리에서 180도 돌고,
  통로 바깥으로 늘어진 곡선을 그려 다음 열 앞에 정확히 마주 선 자세로 도착한다.
  제어점을 통로 바깥으로만 밀면 곡선이 글자 안으로 들어가지 않는다. 다만 두 열의 x
  가 붙어 있으면 곡선이 제자리 왕복으로 퇴화하므로, 같은 통로 안에서는 최소
  `stride`(8m) 떨어진 자리만 고른다.
- **낱자 사이를 두 열 비우면 그 틈이 앞뒤 통로를 잇는 길이 된다**(`space`). 통로를
  건너는 차량은 [뒤 통로의 U자] → [틈을 곧게 관통] → [앞 통로의 U자] 로 간다.
  세 조각의 접선이 전부 세로라 이어 붙는 곳이 없고, 글자를 **가로질러** 내려가는
  움직임이 생겨 화면 위아래가 다 쓰인다.
- **통로를 건널 때도 거리를 따져야 한다**(`cross`). 예전에는 건너는 것은 퇴화하지
  않는다는 이유로 거리를 보지 않았는데, 그러면 한 낱자를 집어 통로를 건너 크게 한
  바퀴 돌고는 **집은 자리 옆에 도로 내려놓는다.** 걸음이 50m 인데 화물은 2m 옮긴
  것이라 그 한 바퀴가 통째로 헛일로 보인다. 낱자 하나(11.9m)는 건너게 묶는다.
  - **거리는 지금 자리가 아니라 집은 자리에서 잰다.** 지금 자리로 재면 놓을 데가
    없어 화면 밖까지 나갔다 온 차량이 집은 자리 옆에 도로 내려놓는다.
  - **빈 채로 옮기는 걸음까지 묶지 않는다.** 집으러 가는 길에도 걸면 고를 일이
    절반으로 줄어 서 있는 시간이 두 배가 된다.
  - **낱자가 줄면 이 값도 줄어야 한다.** 세로 화면은 `compactCell` 로 글자가
    0.66 배가 되는데 이 값만 미터로 두면, 같은 14m 가 거기서는 1.8 낱자가 되어
    세 대가 절반을 서 있었다(정지 15% → 46%). `stride` 는 곡선이 퇴화하지 않을
    최소 거리라 차체에 매인 값이고, 글자를 따르는 것은 이쪽뿐이다.
- **적치대에서 집은 것은 글자에 넣는다.** 왼쪽 적치대에서 집어 오른쪽 적치대에
  놓으면 낱말을 통째로 가로질러 놓고 글자는 하나도 달라지지 않는다. 대신 넣을
  구멍이 없으면 애초에 적치대에서 집지 않는다 — 집어 놓고 갈 데가 없으면 넷이
  다 화물을 든 채 화면 밖에서 굳는다.
- **틈을 고를 때 떠나는 쪽만 보면 안 된다**(`TURNAROUND`). 예전에는 떠나는 열에서만
  4m 를 떼었는데, 틈이 **도착할** 열에 붙어 있으면 빠져나오는 U자가 폭 없는 고리로
  접힌다 — 차량이 순항 속도로 반지름 0.6m 를 돌아 0.17초에 90도 돌아앉았다.
  U자에서 가장 좁게 도는 반지름이 두 열 사이 거리의 0.6 배쯤이라, 양쪽 모두에서
  떼어야 `MIN_RADIUS` 가 지켜진다.
- **여럿이 같은 틈으로 몰리면 그게 곧 "정신없다"다.** 차량마다 몇 번째로 가까운
  틈을 쓸지(`gap`)와 통로에서 도는 반경(`bow`)을 다르게 준다. 앞 통로는 원근이
  크게 잡아 조금만 내려가도 화면 아래를 다 먹으므로 반경을 줄이고(`swing` 0.72),
  뒤 통로는 그 반대다(1.15).
- **손상에 상한이 없으면 글자는 반드시 무너진다.** 보이는 구멍 수는 "미리 비워 둔
  자리 + 지금 무언가를 싣고 가는 차량 수"라, 차량을 늘리는 것만으로 글자가 읽히지
  않게 된다. 그래서 두 가지를 못 박았다 — 동시에 빈 자리는 `damage`(4) 개를 넘지
  못하고, **한 글자에 빈 자리는 하나를 넘지 못한다.** 낱자마다 많아야 한 칸이라
  어느 순간에도 일곱 글자가 다 읽힌다.
- **상한에 걸린 차량을 세워 두면 안 된다.** 집을 자리가 없으면 통로를 한 바퀴 돌고
  (`patrol`), 놓을 자리가 없으면 실은 채로 화면 밖으로 나가 거기서 기다린다 —
  **화면 밖이 곧 넘침 버퍼다.** 무대 위에서 멈춰 선 AMR 은 그 자체로 고장으로 읽힌다.
- 미리 비워 두는 자리는 통로마다 하나씩, 서로 다른 글자에 둔다. 앞뒤 통로는 서로의
  구멍을 채우지 못하므로(앞줄 구멍은 뒤에서 닿지 않는다) 각 통로가 제 몫을 하나씩
  가지고 있어야 아무도 굶지 않는다.

**문구는 가운데 아래에 놓는다**(`align: 'center'`). 옆으로 비켜선 문구는 글자의
왼쪽 절반을 덮는데, 이 장에서 읽어야 하는 것이 바로 그 글자다. 그 대신 세로
오프셋(`frame[1]`)은 문구 블록이 정하는 값이 된다 — 글자가 eyebrow 위로 **완전히**
올라와야 하고, 그만큼 카메라도 물러나야 한다.

앞 통로(카메라 쪽)에서 일하는 차량은 문구 뒤 그라디언트에 잠긴다. 그래도 앞
통로를 없애지는 않는다 — 한쪽 통로만 쓰면 글자의 그 줄만 갉아먹힌다. 대신 앞
통로의 회전 반경을 줄여 차량이 글자 바로 아래(제목 위)에 머물게 한다.

**차량은 넷을 넘기지 않는다.** 다섯이면 `damage` 상한에 걸려 절반이 빈 채로 통로만
돌고, 그것이 곧 "정신없이 움직인다"로 읽힌다. 세로 화면은 `framing` 이 여기서 두 배
가까이 더 빼므로 글자는 `compactCell` 로 따로 줄이고 차량도 셋으로 줄인다.

### 마디를 smoothstep 으로 밀면 마디마다 튀어 나갔다 선다

동선은 [제자리 회전] → [호] → [곧게 들어가기] → [집기/놓기] → [곧게 물러나기] 로
쪼개져 있다. 예전에는 마디마다 진행률에 `smoothstep` 을 물렸는데, 그러면 **마디
하나가 통째로 하나의 출발과 정지**가 된다.

| | smoothstep | 사다리꼴(지금) |
| --- | --- | --- |
| 속도 | 0 → 순항의 1.5 배 → 0 | 0 → `CRUISE` → 0 (가속은 `ACCEL` 로 묶인다) |
| 가속이 가장 큰 곳 | **양 끝**(s″ = ±6) | 순항에 붙고 떨어지는 자리 |
| 마디를 넘을 때 | 반드시 선다 | 양 끝 속도를 받아 이어 붙는다 |

재 보면 마루 속도 5.25 → 3.8 m/s, 가속 2.78 → 2.0 m/s² 로 내려가고 **평균 속도는
거의 그대로다** — 없어진 것이 마루와 정지뿐이기 때문이다. 실제로 붙여 쓰는 것은
호와 곧게 들어가는 구간 하나뿐이다. 통로에서 오던 속도를 문 앞에서 0 으로
떨어뜨리지 않고 `CREEP` 으로 이어받아 팔레트 앞에서 선다.

### 접선은 끝에서 실제 값을 써야 한다

진행 방향을 마디에서 앞뒤로 걸쳐 재면 **끝에서는 걸칠 것이 한쪽뿐이라** 마지막
0.4m 의 현(弦) 방향이 나오고, 그것이 실제 접선에서 `0.2 / 반지름` 만큼 어긋난다.
호가 끝나고 곧게 들어가는 구간으로 넘어가는 그 한 프레임에 차체가 **최대 7도
홱 돌아앉았다.** 지금은 `measure` 가 양 끝 접선을 인자로 받아 그대로 박아 둔다 —
제자리 회전이 겨눈 각과 호의 첫 접선이 같은 값이라 이어 붙는 곳이 없다.

### 호는 팔이 길어도 짧아도 틀린다

제어팔(`reachOf`)이 길수록 통로 바깥으로 넉넉히 부푼 U자가 되지만, 두 자세가
요구하는 것보다 길면 곡선이 **되짚어 나온다** — 순항 속도로 반지름 0.2m 를 돌아
0.17초에 90도 돌아앉는 자리가 그것이다. 그렇다고 줄이기만 하면 양 끝에서 접선을
맞추느라 그 자리에서 꺾인다. `arc` 는 설계값부터 시작해 `SCALES` 를 훑어 가장
좁게 도는 자리가 `MIN_RADIUS` 를 넘는 첫 팔을 쓰고, 끝까지 못 넘으면 그중 가장
넓게 도는 것을 쓴다.

그래도 못 넘는 자리가 남으므로 **좁게 도는 길은 느리게 지난다** — 옆으로 받는
가속을 `LATERAL` 로 묶어 순항 속도를 `sqrt(LATERAL × 반지름)` 으로 내린다.
이 셋(틈 고르기 · 팔 길이 · 속도)을 다 걸고 나서야 요각속도 마루가
20.7 → 2.4 rad/s 로 내려왔다. 제자리 회전의 마루(1.96)와 비슷한 값이라, 도는
동작이 어디서나 같은 속도로 읽힌다.

### 제자리에 선 길은 끝을 못 박을 수 없다

길은 잡을 때 남들이 이미 잡아 둔 길과 견주고, 남의 길은 **끝난 뒤로도 `park`(5초)
만큼 그 끝자리를 잡고 있는 것으로 본다.** 그런데 갈 데가 없어 서 있는 차량은
`park` 이 지나도 그대로 서 있다. 끊어 읽으면 그 자리를 지나는 길을 그어 놓게 되고,
서 있던 쪽은 어떤 일도 열려 있지 않아 **다 막혔을 때 고르는 "가장 널찍한 길"이
그대로 충돌이 된다.**

그래서 제자리에 선 길(자취가 첫 자리에서 0.5m 를 벗어나지 않는 길)은 끝을 못
박지 않는다 — 내 길이 끝날 때까지 그 자리에 있는 것으로 본다.

이건 오래 숨어 있던 함정이라, 고를 일이 넉넉할 때는 거의 드러나지 않았다.
`cross` 를 넣어 고를 일이 줄자 5시드 × 30분에 **1건 → 10건**으로 뛰었고,
이 규칙을 넣은 뒤 **양쪽 다 0건**이 됐다.

### 안개는 재질이 아니라 안개를 밀어내야 한다

⑤ 는 카메라가 44m 위로 올라가 무대 전체가 안개 `near`(34m) 너머 50~79m 에
들어간다. 예전에는 **글자 칸의 재질만** `fog: false` 로 빼 두었는데, 그러면 같은
화물이 실렸을 때와 놓였을 때 다른 재질로 그려진다.

| | 실렸을 때 | 놓였을 때 |
| --- | --- | --- |
| 재질 | 차량이 든 팔레트 (안개 켜짐) | 칸의 인스턴스 (안개 꺼짐) |
| 밝기 | 143 | 167 |

그래서 화물을 들고 다니는 동안 배경색으로 14% 씻겼다가, **내려놓는 한 프레임에
원래 밝기로 튀었다.** AMR 자신도 같은 이유로 계속 흐렸다.

재질마다 `fog` 를 끄는 것으로는 못 고친다 — 그 값은 셰이더 define 이라 켜고 끌
때마다 다시 구워야 하고, 주인공이 든 팔레트는 ④ 에서 **안개에서 걸어 나와야 하는**
바로 그 팔레트다. 대신 안개 거리 자체를 민다 (`lighting.fog.lift`). ⑤ 에서 화면에
남는 것은 광장과 주인공뿐이라 안개가 거리를 알려 줄 일이 없고, near/far 는
유니폼이라 매 프레임 옮겨도 다시 굽지 않는다.

**미는 양은 `written` 을 따른다** — 걷히는 것들과 같이 물러나야 한다. 먼저 걷으면
물러나기로 한 트럭이 안개에서 도로 걸어 나온다.

### 적재장은 꺼지지 않는다. 끝난다

⑤ 로 넘어갈 때 트럭이 제자리에서 옅어지면 그것이 곧 세트 교체다. 대신 `dock.linger`
너머(44m, 안개 속)에 있는 것만 물러나고, 이미 가까이 온 트럭은 평소대로 뒤로 흘러
지나간다 — ④→⑤ 가 **적재장을 지나쳐 나온 것**이 된다. 되감아 올라가면 안개에서
다시 걸어 나오므로 양방향 모두 매끄럽다.

**물러나는 것은 자리가 아니라 흐른 거리로 재야 한다.** 자리로 재면 앞에서 꺼 둔
트럭이 흘러 들어오며 도로 켜지고, 자리로 값을 잠가 두면 반쯤 투명한 채로 굳는다.
`retiredAt` 에 그때의 주행 거리를 적고 `linger.run` 을 흐르는 동안 지우면 둘 다
생기지 않는다.

**대기 화물만 예외다.** 차선 한가운데에 있어 흘려보내면 주인공이 그대로 뚫고
지나간다 — 이것만은 전환과 함께 걷는다.

### 밟았던 함정

- **카메라를 반대편으로 넘길 때는 그 직선이 어디를 지나는지 본다.** 키프레임 사이는
  직선 보간이라, 통로를 건너는 두 장을 그냥 이어 놓으면 그 직선이 지게차를 관통해
  화면이 잠깐 아무것도 아닌 것으로 찬다. 지금 건너는 것은 ①→② 와 ④→⑤ 이고, 앞은
  차량 위 1.7m·옆 4.5m 로 지나고 뒤는 차량 뒤 16m 에서 지난다. 좌우 배치 자체는
  프레이밍 오프셋(`framing.byAlign`)으로 만든다.
- **박스 재질을 다른 크기 지오메트리에 재사용하지 않는다.** 예전 창고 랙이 화물 상자
  재질을 크기가 다른 박스에 얹어서, 텍스처가 늘어나 검은 상자에 흰 십자가 그려졌다.
- **무대 재질은 반드시 복제한다.** glTF 재질은 useGLTF 캐시가 공유하므로, 한 무대를
  흐리는 순간 다른 무대의 같은 부품도 같이 흐려진다.
- **따로 흐릴 것**은 `object.userData.fade` 에 적는다. 무대 전환과 같은 값을 두고 서로
  덮어쓰지 않도록 `setStageOpacity` 가 곱해준다. 재질의 기준 투명도를 런타임에 바꿔야
  한다면 `material.opacity` 가 아니라 `material.userData.baseOpacity` 를 고친다 —
  `applyOpacity` 가 매 프레임 덮어쓴다.
- **불투명도로 투명 재질을 짐작하지 않는다.** `applyOpacity` 는 원래 `transparent` 플래그를
  기억한다. `opacity < 1` 로 판정하면 알파 텍스처를 쓰면서 opacity 가 1 인 재질(라벨
  스프라이트)이 다 드러난 순간 불투명해져 검은 판이 된다.
- **피할 장애물은 앞에서 다가오는 것을 본 것만이다.** 위치만 보고 판정하면 03 이
  시작되는 순간 마침 차량 옆에 있던 장애물이 차량을 조향 없이 옆으로 밀어낸다.
- **무대 객체를 펼쳐 담지 않는다.** `{ name, ...stage }` 로 복사하면 무대가 매 프레임
  고쳐 쓰는 `flowSpeed` 가 복사본에서 얼어붙어 바닥이 첫 프레임 속도로 계속 흐른다.
- **`ShaderMaterial` 은 디졸브를 스스로 받지 못한다.** `applyOpacity` 가 `material.opacity`
  에 넣어 주는 값을 `onBeforeRender` 에서 유니폼으로 옮겨야 한다. 점 크기에 쓰는
  뷰포트 높이도 같은 자리에서 `renderer.getDrawingBufferSize()` 로 받는다 — 인자는
  반드시 `Vector2` 다 (평범한 객체를 넘기면 `target.set is not a function` 으로 죽는다).

모델 자체는 `tools/forklift-model/` 이 실물 URDF 에서 빌드한다 (52MB → 1.4MB).
지게차·팔레트·박스에 더해 적재용 트럭과 랙(`meshes/environment/`)도 같은 파이프라인으로
굽는다. 랙은 같은 재질이 이름만 다른 셋으로 갈려 있어 `usemtl` 을 하나로 모아야
`join()` 이 프리미티브를 합친다 — 안 그러면 랙 하나가 드로우콜 셋이다.

## 측정 붙이기

3D 히어로가 실제로 렌더된 시점에 **한 번** 노출을 보고한다.
WebGL 미지원·모션저감 사용자는 정적 Hero 로 빠지므로 실험에 포함되지 않는다.

```js
window.addEventListener('experiment:exposure', (e) => {
  // e.detail = { experiment: 'hero_scroll_snap', variant: 'snap', source: 'assigned' }
})
// window.dataLayer 가 있으면 { event: 'experiment_exposure', ... } 로도 push 된다
```

`source` 는 배정 경로: `url`(강제 지정) / `stored`(재방문) / `assigned`(신규).
**분석 시 `url` 은 제외한다** — 내부 리뷰용 트래픽이다.

전환 지표는 아직 없다. 히어로 CTA 클릭·`#positions` 도달·지원 완료 중
무엇을 볼지 정해지면 같은 방식으로 이벤트를 추가한다.

## 주의

- 변형은 **마운트 때 한 번만** 정해진다. 도중에 바꾸면 문서 높이·스크롤 동작이
  달라져 보고 있던 위치가 튄다.
- 섹션의 진행률 구간(`range`)은 `vh` 길이에서 **계산된다**. 데이터에 손으로 적지
  않는다 — 길이와 구간을 따로 관리하면 언젠가 반드시 어긋난다.
- 스냅 목표는 각 섹션 구간의 **중앙**(`at`)이다. 마지막 섹션 중앙 이후 남는
  구간(약 7%)은 네이티브 스크롤로 빠져나간다 — 서사가 끝난 뒤라 의도된 동작이다.
